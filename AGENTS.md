# CLAUDE.md

*Animal Kingdom* is a two-player tactical deckbuilding game Martin is designing, meant to become a digital game people play competitively. This repo holds its rules engine, the bots, the simulation tools used to design and balance it, and a terminal interface.

This repo is `game/` in the Animal Kingdom workspace, the folder above it where every session starts and where the skills and guard hooks live; its sibling `design/` is the design sandbox. **Start every session at [`docs/STATUS.md`](docs/STATUS.md)**: where the game stands, its open problems, and what's waiting on Martin. Before reasoning about any card, effect or balance change, read [`docs/rules/mental-model.md`](docs/rules/mental-model.md).

## The trap

The game has no mana, no attack or health, no combat damage. A unit is a single number, strength, and the only resource is the action (two per turn). It borrows Magic/Hearthstone vocabulary ("draw", "removal"), and pattern-matching onto those games ("dies to a ping", "mana curve", "go wide for damage") is the most common mistake made here.

## Commands

Python ≥3.11 with a venv at `.venv`: `python3 -m venv .venv && .venv/bin/pip install -e '.[dev,cli]'` (add `analysis` for self-play training and plots; `pillow` for the design sandbox's card-art tooling, which runs on this venv).

- Tests: `./test` runs both fast tiers at once (the Python fast tier spread over the cores with pytest-xdist, and the web client's `node --test`), about 30 seconds on a quiet machine; `./test <path or -k ...>` runs named Python tests in the foreground in a second or two. Martin never waits on a test: while iterating, run the named tests the change touches, commit as soon as they pass, and run `./test` in the background; a failure is fixed forward in the next commit. `.venv/bin/python -m pytest -q -n auto` adds the bot simulations and training (`@pytest.mark.slow`): background only.
- Web client tests: `cd animal_kingdom/web/test && npm install` once. `npm run test:full` adds the slow ones (about 15 minutes: recorded bot-vs-bot matches checked view by view, clicked matches against the bot, the tutorial played through by clicks; `SHOTS=<dir> node --test tutorial.slow.mjs` saves a 2x screenshot of each lesson); after changes to the engine, the server, or the game screen's drawing and animation, run it in the background and keep working; report only if it fails. The tutorial play-through runs its animations at 20x (`window.AK_SPEED`, set by the test only): about 12 s per run.
- Deploying: `deploy/deploy.sh` in the background, straight after the commit: it runs the web client's fast suite itself and stops on a failure, then builds HEAD on Fly. The image compiles the engine with mypyc and runs the fast Python tier against the compiled modules (`deploy/Dockerfile`); a failure never deploys. A card or client change reuses the compiled engine. The paintings ship as their own image, pushed only when one changes, so a deploy uploads a few MB. It stops a hung Fly after 20 minutes and retries once.
- Long simulations and training (self-play, benchmarks, balance reports) run under `nice -n 15`: they take the idle cores and never slow the tests, builds and conversation of the sessions working beside them.
- Web client: `./play` (serves `animal_kingdom/web/` at localhost:8000). It's the agents' workbench; Martin plays on staging (Hosting, below). A `./play` he does use runs plain, logging: his games, replays and match history are the playtest record. `AK_NO_GAME_LOGS=1` is for test servers only; it keeps nothing, not even the profile database. Terminal: `./run` (interactive setup; `--help` for flags). Recorder UI: `./record` (needs the `tui` extra).
- Card table: `./cards` (http://localhost:8002) shows every card's values and how settled each is, and writes edits into `animal_kingdom/data/cards.json` (the one source of every card: values, status, and the planned animals waiting for a design), `decklists.json` (a starter's cards and name) and `static/art.js` (crops). Cards are cards and decks are decks: a card belongs to no deck (`cards.json` gives it a status: collectible, reserve, tutorial, token, or planned, which the engine skips), and the shipped decks are lists in `animal_kingdom/data/decklists.json`: the starter decks a new profile gets (`starter: true`; they share no card) and the bot decks (`bot: true`, edited there by hand, free to overlap). An agent's edits go through `.venv/bin/python tools/cards/hq.py` (its docstring has the rules: never change a locked value, never set fine or locked); each waits there for Martin's review. A workspace hook refuses every other write to those files.
- Design sandbox: the game's visual design (mockups, design notes, the painted master art that `static/kit2/`, `static/art/` and the key art are exported from) lives in a separate repo, https://github.com/martinmasrna/animal-kingdom-design, cloned beside this one as `../design/` (kept apart only for its size, 1.4 GB of paintings). "Design sandbox" in code comments and docs means that folder; its `AGENTS.md` is the entry point.
- Hosting: live is https://animal-kingdom.fly.dev/ (Fly.io app `animal-kingdom`), staging is https://animal-kingdom-staging.fly.dev/ (`animal-kingdom-staging`: its own machine and database, asleep when unused, so it costs only the minutes Martin plays there). Both deploys ship the committed HEAD, never the working tree: `deploy/deploy.sh` to live, `deploy/deploy.sh staging` to staging.
- Where a change goes (the plan Martin agreed to on 2026-10-24, "Okay then, let's do it"): Martin tests on staging, from any device; nobody else plays there. A change Martin hasn't played yet that changes how the game plays (cards, rules, a new screen) goes to staging, and to live only when he says so; a fix to something that's broken on live goes straight to live. While cards on main wait for his test, live deploys of anything else wait too (a deploy ships all of main): say so instead of deploying. Localhost (`./play`) is the agents' workbench, not where Martin tests.
- Game logs: `deploy/nightly.sh` pulls the human games from live and staging into `results/human_games/` every night at 05:30 and commits them (launchd, `deploy/com.animal-kingdom.nightly.plist`, installed on Martin's Mac; log in `~/Library/Logs/animal-kingdom-nightly.log`). `deploy/deploy.sh pull [staging]` does it by hand.
- Balance report: `./report 200` (round-robin; `--deck X --opponent Y` to scope, `--format files --out DIR` for CSV/JSON, every run records its games to `results/logs/<time>.jsonl`, `--log FILE` to pick the path, `--no-log` to skip). Every simulation keeps its game log: an ad-hoc script calling `run_pairs` passes `log_actions=True` and writes with `sim.replay.write_game_logs`, so questions about how games went are answered from logs, not new runs. Replay a logged game with no bot compute: `.venv/bin/python -m animal_kingdom.sim.replay FILE`.
- Measuring a bot change: the `bot-change` skill (`.claude/skills/bot-change/SKILL.md`); `tools/bot_bench/bench.sh` runs the paired benchmark (`sim.bot_comparison`) on a frozen checkout.
- Deckbuilding and the goodstuff problem: `sim.deck_optimizer`, `sim.metagame_search`, `sim.measure_deck`, `sim.benchmark_set` (see `docs/design/goodstuff.md`).
- After changing `cards.json`, regenerate the deck docs' card tables: `.venv/bin/python -m animal_kingdom.render.deck_docs`.

The ruleset (map_b, two actions per turn, Draw draws 2) is the default everywhere; no flags needed. `results/` is untracked except `results/human_games/`: human recordings are irreplaceable, so commit them.

## Invariants

- `engine/` is stdlib-only and transport-agnostic; file loading happens only at construction. `apply_action` validates every action; only bot search, which applies actions it just generated, passes `validate=False`.
- Card numbers live in `cards.json` (strength, food cost, text) or `engine/config.py` (effect magnitudes), never as literals in effect code. `test_card_text_consistency.py` checks printed numbers against config; extend it when a card gains a new kind of number.
- Bots are generalist (no deck slugs, archetype names or card ids in policy) and honest (never read hidden information). Both are regression-tested.
- A card's id names its animal and never follows its display name: `<animal>` for a common or rare, `<animal>_legend` for a legendary (`_2`, `_3` for later legendaries of the same animal, in deck-code order). A card whose animal changes gets a new id with `tools/cards/hq.py rename OLD NEW`, which carries it everywhere, keeps its deck-code number and maps the old id for saved decks, replays and saved matches. `test_card_ids.py` holds it.
- Never nerf a card to fix a bot. A simulation finding is either a card signal or a pilot flaw; triage it first (the `balance-eval` skill).
- Balance and bot claims need ≥200 games per matchup, paired seeds, both seats.
